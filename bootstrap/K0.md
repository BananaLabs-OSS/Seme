# Seme K0 bootstrap execution format

K0 is the portable execution boundary between platform-specific ignition and
the Seme kernel. It is not canonical Seme storage and is not a user-facing
language. Platform executors implement the same frozen K0 profiles.

K0 is currently a draft. Profile P0 proves deterministic parsing and execution
before functions, effects, and control flow are added.

Profile P1 adds functions and call frames while retaining the P0 instruction
semantics.

Profile P2 adds bounded byte buffers and declared host capabilities so portable
compiler programs can read source and emit artifacts.

## P0 image

```text
magic              8 bytes: 53 45 4d 45 2d 4b 30 00 ("SEME-K0\0")
version            canonical ULEB128: 1
local_count        canonical ULEB128, maximum 256
instruction_count  canonical ULEB128, maximum 65535
instructions       exactly instruction_count instructions
```

All runtime values are unsigned 64-bit integers in P0. Arithmetic wraps modulo
2^64. Boolean results are canonical `0` or `1`.

## P0 instructions

| Opcode | Operation | Stack |
|---:|---|---|
| `00` | `return` | `value --` |
| `01` | `const.u ULEB` | `-- value` |
| `02` | `local.get ULEB` | `-- value` |
| `03` | `local.set ULEB` | `value --` |
| `04` | `drop` | `value --` |
| `05` | `dup` | `value -- value value` |
| `10` | `add` | `left right -- result` |
| `11` | `sub` | `left right -- result` |
| `12` | `mul` | `left right -- result` |
| `1a` | `eq` | `left right -- bool` |
| `1b` | `lt.u` | `left right -- bool` |
| `20` | `jump TARGET WITNESS` | `--` |
| `21` | `branch.false TARGET WITNESS` | `condition --` |

`TARGET` is a zero-based semantic instruction index. `WITNESS` is the byte
offset of that instruction from the beginning of the instruction sequence.
It is derived bootstrap layout data, not control-flow identity. P0 validates
both bounds during execution; a release validator must additionally prove that
every witness lands on the declared instruction boundary before execution.

The first instruction cannot read an uninitialized local. `return` must be the
last declared instruction and must observe exactly one stack value. Falling off
the instruction sequence, trailing bytes, invalid opcodes/indices, malformed
ULEB values, stack underflow/overflow, and uninitialized reads are errors. A
taken branch resets the remaining-instruction budget from `TARGET`.

The Linux executor returns the low eight bits of the K0 result as its process
status for P0 conformance. Later profiles return structured values through a
platform-neutral invocation contract.

## Exit statuses

- program result: `0` through `63`, when representable by the P0 fixture;
- `64`: invalid executor invocation;
- `65`: malformed or invalid K0;
- `74`: operating-system I/O failure.

Conformance fixtures avoid program results `64`, `65`, and `74` so bootstrap
failure remains distinguishable.

## P1 function image

```text
magic              "SEME-K0\0"
version            canonical ULEB128: 2
function_count     ULEB, 1 through 16
functions          repeated Function
entry_function     ULEB function index

Function:
  parameter_count  ULEB, at most local_count
  local_count      ULEB, maximum 64
  instruction_count ULEB, 1 through 65535
  code_size        ULEB, nonzero
  code             exactly code_size bytes
```

P1 adds opcode `30 call FUNCTION_INDEX`. Arguments are popped in reverse order
into parameter locals `0..n-1`. Every invocation receives isolated locals and
initialization state. Call depth is limited to 31 nested calls. `return` requires
exactly one value above the frame's incoming stack base and must be the final
declared instruction in that function.

The entry function must have zero parameters. Bytes after `entry_function` are
rejected before execution. Function code remains lazily validated on execution
in P1; whole-image validation is a required release gate before K0 is frozen.

The current Linux executor now performs a structural preflight of every P1/P2
function before execution. It verifies exact code sizes, canonical operands,
known opcodes, local and call indices, final returns, capability declarations,
semantic branch targets, and byte-position witnesses—including unreachable
functions. Control-flow type/stack merging and path-sensitive initialization
remain responsibilities of the forthcoming portable Kernel validator.

## P2 capabilities and bytes

P2 uses image version `3` and inserts `capability_mask ULEB` before
`function_count`. Unknown bits are rejected:

| Bit | Capability |
|---:|---|
| `1` | process arguments |
| `2` | filesystem read |
| `4` | filesystem write |

P2 adds bounded byte-buffer handles. At most 16 buffers may exist and each is
limited to 65536 bytes. Handles remain bootstrap values; they do not establish
Seme's eventual memory model.

| Opcode | Operation | Stack |
|---:|---|---|
| `40` | `bytes.len` | `handle -- length` |
| `41` | `bytes.get` | `handle index -- byte` |
| `42` | `buffer.new` | `capacity -- handle` |
| `43` | `buffer.push` | `handle byte -- handle` |
| `60` | `arguments.count` | `-- count` |
| `61` | `arguments.get` | `index -- handle` |
| `62` | `fs.read` | `path -- content` |
| `63` | `fs.write` | `path content -- 0` |

Program arguments exclude the executor and K0 image path. Files larger than one
P2 buffer and paths containing zero bytes are rejected. `fs.write` creates or
truncates its destination with mode `0644`. Every effect checks the image's
declared capability before touching the host.
